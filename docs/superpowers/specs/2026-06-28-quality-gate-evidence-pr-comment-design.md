# Quality Gate Evidence in PR Description

**Date:** 2026-06-28
**Status:** Approved

## Problem

When `requiredQualityGates` are configured (e.g. in `.zeroshot/settings.json`), validators collect evidence — the command run, exit code, and output — for each gate. This evidence gates the git-pusher handoff but is never surfaced anywhere visible. Additionally, PRs created by the git-pusher currently have no description — the `--body` is `"Closes #{{issue_number}}"` and nothing else.

## Goal

When the git-pusher creates a PR/MR, write a description containing:

1. **An overview** of what changed (generated by the agent from `git log` / `git diff --stat`).
2. **Quality gate evidence** — gate ID, pass/fail status, command run, exit code, and truncated output — when `requiredQualityGates` are configured.

This applies to all three supported platforms (GitHub, GitLab, Azure DevOps).

## Constraints

- Output truncation: last 5 lines of output per gate, capped at 500 characters total. Append `[truncated]` if either limit was applied.
- When `requiredQualityGates` is empty, the description still includes the overview + `Closes #{{issue_number}}` — no quality gate section.
- No new infrastructure — uses the existing `triggeringMessage` data conduit and `generatePrompt` conditional step pattern.
- The description is constructed by the agent at PR creation time (STEP 5), not in a separate post-creation step.

## Architecture

### Data flow

```
validator VALIDATION_RESULT message
  └─ content.data.qualityGates: [{id, status, evidence: {command, exitCode, output}}]
        │
        ▼
agent-context-sections.js  (new: buildQualityGateEvidenceSection)
  └─ Formats evidence as plain text, applies truncation
  └─ Appended to triggeringMessage section in agent context
        │
        ▼
git-pusher LLM agent  (sees evidence in its context)
  └─ STEP 5: collects git log/diff for overview, constructs PR body,
             creates PR with --body containing overview + quality gate section
```

### Why this approach

The `SHARED_TRIGGER_SCRIPT` runs in a read-only VM sandbox (`ledger`, `cluster` read-only). It cannot write files or call `store.set()`. The `triggeringMessage` is already injected into the agent context via `buildTriggeringMessageSection` — extending it to surface `content.data.qualityGates` is the idiomatic path. Building the PR body inside STEP 5 (rather than a separate comment step) is simpler and keeps all PR creation in one atomic step.

### PR description format

```markdown
## Overview

<1–3 sentence summary of what changed, generated from git log/git diff --stat>

Closes #{{issue_number}}

## Quality Gate Evidence

| Gate  | Status  | Exit | Command                                      |
| ----- | ------- | ---- | -------------------------------------------- |
| tests | ✅ PASS | 0    | `pip install -e '.[dev]' -q && pytest`       |
| lint  | ✅ PASS | 0    | `pip install -e '.[dev]' -q && ruff check .` |

<details><summary>tests output</summary>
```

32 passed in 1.72s

```

</details>

<details><summary>lint output</summary>

```

All checks passed!

```

</details>
```

When `requiredQualityGates` is empty, the `## Quality Gate Evidence` section is omitted.

## Component Specifications

### 1. `src/agent/agent-context-sections.js`

**New function:** `buildQualityGateEvidenceSection(qualityGates)`

Input: array of quality gate objects from `triggeringMessage.content.data.qualityGates`.

Output format (plain text, appended after existing `content.text` block):

```
Quality Gate Evidence:
- [tests] PASS | exit=0 | cmd: pip install -e '.[dev]' -q && pytest
  output:
  32 passed in 1.72s

- [lint] FAIL | exit=1 | cmd: pip install -e '.[dev]' -q && ruff check .
  output:
  src/foo.py:10:1: E302 expected 2 blank lines
  [truncated]
```

**Truncation logic (applied per gate):**

1. Split output on newlines, take the last 5 lines.
2. Join and take the last 500 characters of the result.
3. If either limit was applied, append `[truncated]` on a new line.
4. If output is empty or missing, omit the `output:` block.

**Integration:** Call `buildQualityGateEvidenceSection` from `buildTriggeringMessageSection` when `triggeringMessage.content?.data?.qualityGates` is a non-empty array.

**Returns empty string when:**

- `qualityGates` is absent, null, or not an array.
- The array is empty.

### 2. `src/agents/git-pusher-template.js`

#### `generatePrompt` — extended STEP 5

STEP 5 is extended to instruct the agent to construct a PR description before running `createCmd`. The `createCmd` in `getPlatformConfig` changes from a single-line shell command to a reference pattern — the agent builds the body and passes it via a heredoc.

The updated STEP 5 instruction:

````
### STEP 5: CREATE THE PR (MANDATORY)

Before creating the PR, collect the change overview:
```bash
git log --oneline HEAD~5..HEAD
git diff --stat HEAD~1
````

Use this to write a 1–3 sentence overview of what was implemented.

Then construct the PR body and create the PR:

```bash
PR_BODY="$(cat <<'EOFBODY'
## Overview

<your 1–3 sentence overview here>

Closes #{{issue_number}}
<quality gate section here when requiredQualityGates > 0, using "Quality Gate Evidence" from your context>
EOFBODY
)"
<platform createCmd using $PR_BODY>
```

The quality gate section (when present) must follow this format:

## Quality Gate Evidence

| Gate | Status                             | Exit   | Command |
| ---- | ---------------------------------- | ------ | ------- |
| <id> | ✅ PASS / ❌ FAIL / ⚠️ UNAVAILABLE | <exit> | `<cmd>` |

<details><summary><id> output</summary>

```
<truncated output from context>
```

</details>
```

Platform `createCmd` values updated to accept `$PR_BODY`:

| Platform       | createCmd pattern                                                                                               |
| -------------- | --------------------------------------------------------------------------------------------------------------- |
| `github`       | `gh pr create --head "$(git branch --show-current)"${prBase} --title "feat: {{issue_title}}" --body "$PR_BODY"` |
| `gitlab`       | `glab mr create --title "feat: {{issue_title}}" --description "$PR_BODY"`                                       |
| `azure-devops` | `az repos pr create --title "feat: {{issue_title}}" --description "$PR_BODY"`                                   |

#### CRITICAL RULES update

One new bullet added:

```
- STEP 5 requires constructing the PR body before running the create command — run git log/diff first
```

## Testing

### Unit tests (existing test file: `tests/required-quality-gates-context.test.js`)

- `buildQualityGateEvidenceSection` with a passing gate: output contains gate ID, status, command, exit code, and output.
- `buildQualityGateEvidenceSection` with a failing gate: status shows FAIL, output block present.
- Truncation: output > 5 lines is truncated to last 5 lines; output > 500 chars is capped and marked `[truncated]`.
- Empty/null qualityGates returns empty string.
- Output absent: no `output:` block rendered.

### Unit tests (`tests/structuredOutput-mapping.test.js` or new file)

- `getPlatformConfig('github', ...)` `createCmd` contains `$PR_BODY`.
- `getPlatformConfig('gitlab', ...)` `createCmd` contains `$PR_BODY`.
- `getPlatformConfig('azure-devops', ...)` `createCmd` contains `$PR_BODY`.
- `generatePrompt` with `requiredQualityGates: []` includes STEP 5 overview instructions but no quality gate section instructions.
- `generatePrompt` with `requiredQualityGates: [{id: 'tests'}]` includes STEP 5 quality gate section instructions.

## Out of Scope

- Posting evidence when `requiredQualityGates` is empty (overview-only description still added).
- Retrying description construction on failure.
- Including validator `criteriaResults` beyond the `qualityGates` array.
- Evidence from non-passing clusters (git-pusher only fires when all gates pass).
